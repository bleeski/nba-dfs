## New issues

### R2-I-01: Multi-entry Goal 1 in `docs/BRIEF.md` ("every entry's top-1% winnings count, not only the best entry's") breaks submodular coverage and double-counts 1st-place equity unless rank self-displacement is modeled
**Severity:** Blocker · **Affects:** Goal 1, Build · **Lands by:** Before C01 · **Confidence:** High · **Applies to:** `docs/BRIEF.md` (§"The two goals"), `ADR-007`, `ADR-024`, `C01`, `C08`, `C09`

**Nearest decided item:** `ADJUDICATION Entry 5` (`ADR-024`, Redefinition of Goal 1 as Top-1% Prize Equity). That ruling decided to weight top-1% finishes by dollar prize equity rather than binary probability, whereas this issue is about the new multi-entry aggregation rule added in `docs/BRIEF.md` (*"every entry's top-1% winnings count, not only the best entry's"*) and how it breaks `ADR-007`'s greedy selector.

**What it is.** `docs/BRIEF.md` defines Goal 1 with the sentence: *"Top-1% places are `max(1, floor(0.01 x field size))`, so any field under 200 entries counts first place only (Decision D10). In a multi-entry contest every entry's top-1% winnings count, not only the best entry's."* Right below that, `docs/BRIEF.md` asks: *"In a 20-entry contest, does it build 20 independent entries or a correlated 20-entry portfolio? Explain the difference in simple terms and state which one we build."* Meanwhile, `ADR-007` (`Accepted, revised 2026-10-14`) selects portfolios via greedy selection per contest on Goal 1.

**Why it's worth solving.** There is a fundamental mathematical conflict between summing marginal top-1% winnings across entries (`sum_{L in E_c} Equity(L, s)`) and building a diversified, scenario-covering multi-entry portfolio:
1. **Linearity of expectation destroys scenario coverage:** If the objective in scenario `s` is the simple sum of each entry's marginal top-1% prize equity against the opponent field (`sum_{L in E_c} Equity(L, s)`), then by linearity of expectation, the value of a 20-entry portfolio is just the sum of the 20 individual lineups' expected values (`sum_{L in E_c} E[Equity(L)]`). Adding a second lineup `L_2` that wins in the **exact same 1% of scenarios** as `L_1` gets the **full marginal reward**, with zero diminishing returns! A greedy selector optimizing an unadjusted sum simply picks the #1 highest-EV lineup and 19 tiny perturbations of that same game stack, recreating the exact `nfl-dfs` failure (`RR2` §7: *"Engine portfolios look like one lineup with 17 perturbations"*).
2. **Self-displacement and double-counting in small fields (`k_c = 1`):** In any multi-entry contest under 200 entries (such as a 105-entry 3-max or 150-entry 20-max, `R6` §5), `k_c = 1` (only 1st place counts). In a given scenario `s`, **only one lineup can win unsplit 1st-place money**. If two of your own entries both beat every opponent in scenario `s`, one finishes 1st and your other entry is pushed down to 2nd place (outside `k_c = 1`!), or if they tie, they split the single 1st-place prize with each other. Summing marginal `Equity(L, s)` across your entries counts two 1st-place prizes in a contest that only has one!

**Recommended solution and why.** Before `C01` locks `CONTRACTS.md`, specify **Rank-Displaced Joint Settlement** as the multi-entry Goal 1 formula in `docs/BRIEF.md`, `ADR-024`, `ADR-007`, and `C08`/`C09`:
- In scenario `s`, sort our chosen entries `E_c = {L_1, ..., L_n}` in descending order of their simulated scores: `X_{(1)}(s) >= X_{(2)}(s) >= ... >= X_{(n)}(s)`.
- If entry `L_{(m)}` is our `m`-th highest-scoring distinct lineup in scenario `s` and `r_opp(L_{(m)}, s)` opponents strictly beat it, its **realized contest rank** is `r_total = r_opp + (m - 1) + 1` (because `m - 1` of our own higher-scoring entries sit above it!). If `r_total > k_c`, its top-1% prize equity in scenario `s` is `0`.
- Why this works: Because the top-1% payout curve `W_c(r)` is steep and convex decreasing in rank `r` (and drops to `0` at `r > k_c`), our `m`-th entry in the *same* scenario gets pushed down to rank `r_opp + m`, earning `W_c(r_opp + m) << W_c(r_opp + 1)` (and `0` when `k_c = 1`!). That makes the joint multi-entry objective **strictly monotone submodular** (diminishing returns in every scenario), preserves `ADR-007`'s greedy guarantee, counts every entry's true top-1% winnings without double-counting, and forces the 20 entries to spread across different game scripts!

### R2-I-04: Single-file cross-contest export in `docs/BRIEF.md` and `ADJUDICATION Entry 2` ("output a single exportable entry file across all of them") is rejected by DraftKings across Classic and Showdown draft groups
**Severity:** Blocker · **Affects:** Opening night, Build, Workload · **Lands by:** Before C01 · **Confidence:** High · **Applies to:** `docs/BRIEF.md` (§"Portfolio structure and scale"), `docs/review/ADJUDICATION.md` (`Entry 2`), `C02`, `C03`

**Nearest decided item:** `ADJUDICATION Entry 2` (Single-Batch Contest Execution). The ruling to run all of a night's contests in a single unified batch is sound, but its file-output requirement (*"generates one consolidated DK upload CSV file"*) violates verified DraftKings CSV mechanics (`R6` §2.3).

**What it is.** `docs/BRIEF.md` states: *"The engine must accept any set of DK contests, run them in one batch, and output a single exportable entry file across all of them (entry 2)."* `ADJUDICATION.md` (`Entry 2`) states: *"The engine accepts any set of DraftKings contests entered by the user for a night, executes them in a single unified run, and generates one consolidated DK upload CSV file."*

Multiple contests *within the same draft group* (for example, a Single Entry, a 3-max, a 20-max, and a 150-max all on the Main Classic slate) already live in the same `DKEntries.csv` file, so they consolidate into one file per draft group, never one file across different draft groups.

### R2-I-05: Goal 2 ("severe drawdown: total payout < 25% of fees", `ADR-025`) cannot be evaluated with binary min-cash bitsets (`hc[c, L, s]`) and requires a capped dollar-payout accumulator across all entries
**Severity:** Major · **Affects:** Goal 2, Both goals, Build · **Lands by:** Before C08 · **Confidence:** High · **Applies to:** `docs/BRIEF.md` (§"The two goals"), `ADR-025`, `CONTRACTS.md`, `C08`, `C09`, `C12`

**Nearest decided item:** `ADJUDICATION Entry 9` (`ADR-025`, Goal 2 defined as severe drawdown `< 25%` of fees). The ruling adopted the 25%-of-fees drawdown definition, and this item addresses the execution gap between that dollar-recovery definition and the binary cash-line bitset data structures in `C08`/`C09`/`C12`.

**What it is.** Under v3 (`R2-optimization-methods.md` §3.3, `R9` line 41), Goal 2 was literal zero-cash washout, so `C08` only needed to compute a single min-cash score threshold `Tc[c, s]` per contest and scenario, and `C09`/`C12` stored a 1-bit indicator `hc[c, L, s] in {0, 1}` ("did lineup `L` beat `Tc[c, s]`?") and checked whether `max_{L in E_c} hc[c, L, s] > 0`. Under v4 (`docs/BRIEF.md`, `ADR-025`), Goal 2 is the probability that **total dollar winnings across all contests and entries in scenario `s` fall below `0.25 x Total_Nightly_Fees`**.

**Why it's worth solving.** If `C08` and `C12` retain binary `hc[c, L, s]` bitsets or only track the single best-scoring entry `B_c(s)` per contest:
1. **You cannot sum binary indicators across contests of different entry fees and payout tiers to check if dollar winnings reached 25% of fees.** On a $100 night (say, twenty $1 entries in a Classic 20-max, one $20 Single Entry, and twelve $5 Showdown entries), recovering `$25` (`25%` of fees) in scenario `s` might come from one entry finishing 40th for `$30`, OR from eight $1 entries min-cashing for `$2` each plus two $5 entries min-cashing for `$7.50` each (`$16 + $15 = $31 >= $25`).
2. **Evaluating only the best entry `B_c(s)` per contest undercounts multi-entry cashes by 5x to 20x.** In a 20-entry contest where 7 of your 20 entries min-cash for `$2` each, `B_c(s)` only sees the single best entry (`$2`) and misses the other `$12` of fee recovery!

**Recommended solution and why.** In `CONTRACTS.md`, `C08` (`Field model and settlement`), and `C12` (`Insurance control`), replace the binary cash bitset `HC[c]` (`uint64` words) with a **Capped Dollar-Payout Matrix `P_recovery[c][L, s]`** stored as `uint16` cents (or `$0.05` units), capped at the night's drawdown target `D_target = 0.25 x Total_Fees`:
- In `C08`, for each candidate lineup `L` in contest `c` and scenario `s`, map `L`'s score `X_L(s)` against the opponent score distribution `F_{c,s}` and the contest's payout table `W_c(rank)` to get expected dollar payout `p_{c,L}(s) = min(D_target, Payout_c(L, s))`.
- For any portfolio `E = {E_c}`, total fee-recovery toward the drawdown floor in scenario `s` is `R(E, s) = min(D_target, sum_{c} sum_{L in E_c} p_{c,L}(s))`, and `Goal 2` is simply `P(Severe Drawdown) = mean_s(1[R(E, s) < D_target])`.
- In `C12`'s insurance swap search, maintaining the vector `Tot_Payout[s] = sum_{c} sum_{L in E_c} p_{c,L}(s)` across `S_V = 15,000` validation scenarios takes `30 KB` of RAM, and testing a candidate swap `e -> L` in contest `c` is a single vectorized addition `Tot_Payout + p_{c,L} - p_{c,e} >= D_target` (`< 0.2 seconds` for the entire search!).

### R2-I-06: `ADR-020` ("Eighth-point Captain totals") and `C05`/`C08` tie-splitting need exact integer-eighth quantization to avoid `85.875` vs. `85.88` display mismatches
**Severity:** Major · **Affects:** Goal 1, Build · **Lands by:** Before C05 · **Confidence:** High · **Applies to:** `docs/adr/README.md` (`ADR-020`), `C05-scoring-history-priors.md`, `C08-field-model-and-settlement.md`

**Nearest decided item:** `ADR-020` (revised 2026-10-14: *"Versioned scoring adapter with nightly self-checks; eighth-point Captain totals"*). This item addresses a subtle conflict between internal eighth-point Captain math (`0.125`) and DraftKings' 2-decimal display rounding (`85.88`) in `C05`'s nightly self-check and `C08`'s tie-detector.

**What it is.** `ADR-020` was revised on 2026-10-14 from "quarter-point-exact form" to **"eighth-point Captain totals."** In DraftKings NBA scoring (`NBA Classic.txt`, `NBA Showdown Captain Mode.txt`), every base stat is a multiple of `0.5` except Rebound (`+1.25`). Therefore, a UTIL player's score is always an exact multiple of `0.25` (`1/4`), and a Showdown Captain's score (`1.5 x UTIL`) is an odd multiple of `0.125` (`1/8`, ending in `.125`, `.375`, `.625`, or `.875`) whenever the Captain records an **odd number of rebounds** (verified in `R6-draftkings-mechanics.md` §4b: Jayson Tatum's 7 rebounds gave `1.5 x 57.25 = 85.875`).

**Why it's worth solving.** Two bugs arise if `C05` and `C08` are not aligned on eighth-point representation:
1. **False alarms in `C05` / `C13`'s morning standings self-check (`ADR-020`):** In `R6` (§4b line 245), DraftKings' `contest-standings.csv` right-hand table displays Jayson Tatum's Captain `FPTS` rounded to two decimal places (`85.88`), and `ADR-020` states that a morning scoring mismatch *"stops learning for that night."* If `C05` computes `85.875` and asserts `CPT_FPTS == 1.5 x UTIL_FPTS` on the standings file's 2-decimal strings (`85.88 / 57.25 = 1.500087`), or compares `85.875` to `85.88` with a tight tolerance, every Showdown Captain with an odd rebound count will trigger a false mismatch!
2. **Floating-point tie-splitting bugs in `C08` (`Settlement`):** In binary IEEE-754 floating point (`float32` / `float64`), eighths (`0.125 = 2^-3`) are **100% exact**, whereas 2-decimal rounded numbers (`0.88`) are repeating binary fractions (`85.88000488...`, which is why `R6` §2.4 saw `103.18001` and `93.149994` in standings files). If `C08` rounds Captain points to 2 decimals before summing lineup scores, two identical-score lineups ordered differently in the matrix multiply can differ by `1e-5` and fail an exact tie check `X_L(s) == X_opp(s)`!

**Recommended solution and why.** Specify in `CONTRACTS.md`, `C05`, and `C08`:
1. Inside `C05`, `C07`, and `C08`, never round Captain scores to 2 decimal places: keep them as exact multiples of `0.125` (or store simulated scores as integer eighths `int16` of `round(8 * score)` so tie comparisons in `C08` are exact integer equality!).
2. In `C05` and `C13`'s morning standings check against DraftKings' 2-decimal `FPTS` column, test `abs(dk_displayed_fpts - exact_score) <= 0.005 + 1e-9` (which accepts `85.88` for `85.875` while rejecting any `0.125` or `0.25` scoring error).

### R2-D-02: Soft-decay scenario weighting (`gamma = 0.20`) in `C09` greedy selection to answer `BRIEF.md`'s correlated multi-entry portfolio question
**Affects:** Both goals · **Lands by:** Before C09 · **Effort:** Low · **Confidence:** High · **Applies to:** `C09-candidates-selection-baseline-night.md`, `ADR-007`, `docs/BRIEF.md`

This idea directly answers the open question in `docs/BRIEF.md` (*"In a 20-entry contest, does it build 20 independent entries or a correlated 20-entry portfolio?"*) and prevents greedy selection from over-stacking the single highest-probability game script in `entries 2..6`.

**What it is.** When building a 20-entry portfolio, there are two ways a greedy loop can behave after picking Lineup 1:
1. **Why it's worth solving.** To maximize **both** Goal 1 (top-1% prize equity across scenarios) and Goal 2 (avoiding `< 25%` fee-recovery drawdown nights), each individual lineup should be **internally positively correlated** (a coherent game script stack), while the 20 lineups in the portfolio should be **externally negatively correlated / orthogonal across game scripts** so that if Game 1 busts, entries built on Games 2 and 3 still cash and hit top 1%.
